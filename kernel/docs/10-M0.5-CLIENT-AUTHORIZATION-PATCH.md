# M0.5 Client Authentication & Authorization Patch

Status: **COMPLETED**  
Patch line: **v0.9.2**

## Scope

This patch addresses one focused M0.5 security issue only: separating an external client's self-declared identity from the identity that the Host actually authenticates and authorizes.

## Problem found

Before this patch, the external Unix-socket client sent an `Envelope` containing `caller`, and the Client Gateway used that value as the authorization identity.

That meant a client could attempt to claim:

```text
caller = local-cli
```

and inherit grants intended for `local-cli` without first proving that identity.

The existing `Manifest declaration + Host Grant` split for plugin-to-plugin calls was directionally correct, but the external-client identity boundary was incomplete.

## Final model

The path is now:

```text
Client-supplied identity + credential
        |
        v
Client Gateway authentication
        |
        v
Host-derived authenticated identity
        |
        v
Authorization grant check
        |
        v
Capability Router
```

The payload envelope's `caller` field is not trusted for external clients. The Gateway overwrites caller context with the authenticated identity before routing.

## Authentication is not authorization

These are deliberately separate:

### Authentication

Answers:

> Who is this external caller?

The reference implementation maps a client identity to a SHA-256 token digest in Host Policy and compares the presented token in constant time.

### Authorization

Answers:

> May this authenticated identity invoke this capability?

The existing `authz.Engine` checks Host Policy grants such as:

```json
{
  "read-only-cli": {
    "capabilities": [
      "work.get@1",
      "event.journal.replay@1"
    ]
  }
}
```

Therefore a valid `read-only-cli` credential still cannot call `work.create@1`.

## Plugin authorization remains two-key

A plugin capability call still requires both:

1. the capability is declared in `manifest.consumes`; and
2. Host Policy grants the plugin identity that capability.

A plugin cannot gain capability access merely by editing its own Manifest.

## Fail-closed policy loading

The Kernel now treats authorization policy loading/validation failure as fatal startup configuration failure instead of logging the error and continuing ambiguously.

Client credentials are validated so that every authenticated client identity also has an explicit authorization grant.

## Wire boundary

External clients now send a Client Gateway wire request:

```text
WireRequest {
    identity
    token
    envelope
}
```

`WireRequest` belongs to the external Client Gateway transport boundary. It is intentionally **not** added to the plugin runtime `Envelope`, so transport authentication does not contaminate the language-neutral plugin protocol.

## Tests added

Unit tests verify:

- correct token authenticates the intended identity;
- another identity's token does not authenticate;
- unknown identities fail;
- client-prepared envelopes cannot preserve a self-supplied `caller`;
- policy credentials without matching grants are invalid.

The M0.5 vertical qualification additionally verifies:

- using the valid `local-cli` token while claiming identity `evil` fails;
- `read-only-cli` authenticates but cannot invoke `work.create@1`;
- existing authorized external streaming still works.

## Security non-goals

The SHA-256 token fixture is a portable reference authentication mechanism, not a production credential system.

Production hardening should preserve the same separation while replacing the credential backend with one or more of:

- Unix peer credentials / OS identity;
- local keychain or secret broker;
- mutually authenticated TLS for remote clients;
- short-lived signed tokens;
- project/user scoped policy issuance.

This patch does not implement OS filesystem/network sandboxing, capability-grant administration UI, delegated identities, remote multi-user tenancy, or secret rotation.

## Architectural result

After this patch:

```text
Declared dependency != authorization grant
Claimed identity      != authenticated identity
Authenticated identity != authorized capability
```

All three boundaries are explicit.
