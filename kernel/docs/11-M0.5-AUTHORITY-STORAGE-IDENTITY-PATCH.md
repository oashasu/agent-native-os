# M0.5 Stateful Authority Storage Identity Patch

Status: **COMPLETED**  
Patch line: **v0.9.3**

## Scope

This patch closes one focused stateful-provider gap only: a provider can no longer join an existing logical `service + authority` while pointing at a different storage namespace.

## Problem found

v0.9.2 already prevented automatic failover from one stateful authority to a different authority. However, `authority` was still primarily a provider-declared string.

Before this patch two providers could both claim:

```text
service   = default-work-registry
authority = workdb-main
```

while declaring different runtime storage locations:

```text
provider A -> state-authority/workdb-main
provider B -> some-other-state
```

The Registry would have treated them as replicas of the same authority. That makes `authority` too weak to function as a real state ownership boundary.

## Final rule

For a stateful capability:

```text
Logical Authority
    = service + authority
```

and that logical authority is bound to exactly one declared storage identity:

```text
runtime.data_namespace
```

All runtime replicas serving the same `service + authority` must declare the same `data_namespace`.

If a second provider declares the same authority but a different storage identity, runtime registration fails closed.

## Why `data_namespace` is mandatory for stateful plugins

A stateful provider cannot safely rely on the default per-plugin namespace because replicas have different plugin identities.

Therefore any manifest exporting a stateful capability must now explicitly declare:

```json
{
  "runtime": {
    "data_namespace": "state-authority/workdb-main"
  }
}
```

This makes the storage identity reviewable before runtime.

## Registry behavior

`Registry.RegisterRuntime` now performs authority-storage preflight before mutating provider state.

For every stateful export it checks:

```text
(service, authority) -> data_namespace
```

If an existing claim disagrees, registration returns an error and the conflicting provider is not partially registered.

The Supervisor treats this as runtime startup failure and terminates the rejected process.

## Valid replica example

```text
org.vibe.work.registry
  service: default-work-registry
  authority: workdb-main
  data_namespace: state-authority/workdb-main

org.vibe.work.registry.replica
  service: default-work-registry
  authority: workdb-main
  data_namespace: state-authority/workdb-main
```

Both are allowed.

## Rejected replica example

```text
provider A
  service: default-work-registry
  authority: workdb-main
  data_namespace: state/work-a

provider B
  service: default-work-registry
  authority: workdb-main
  data_namespace: state/work-b
```

Provider B is rejected even if it is healthy and exports the same capability contract.

## Architecture fitness

The architecture check now verifies that:

- every stateful export has `service` and `authority`;
- every stateful plugin has an explicit `runtime.data_namespace`;
- manifests claiming the same `service + authority` agree on storage identity.

## Tests added

Unit tests cover:

- stateful manifest without `data_namespace` is rejected;
- same authority + different storage identity is rejected;
- rejected provider is not partially registered;
- same authority + same storage identity is accepted as a replica;
- existing different-authority failover protection remains intact.

The existing M0.5 integration flow still passes, including the work-registry replica path because both replicas intentionally share the same storage identity.

## Important non-goal

This patch does **not** yet prove safe concurrent multi-writer leadership for stateful replicas.

It establishes:

```text
same authority => same declared storage identity
```

It does not yet establish:

```text
exactly one active writer / lease / fencing token
```

A later adversarial patch should address active-writer authority, lease/fencing, and operator-controlled failover if the storage technology cannot safely support multiple writers.

## Architectural result

After this patch the stateful model is more precise:

```text
Capability
    != Logical Service
    != Authority
    != Runtime Provider

Authority
    -> one Storage Identity
    -> zero or more compatible runtime replicas
```

This closes the specific gap where an unrelated state store could masquerade as an existing authority merely by copying its authority name.
