# ADR-003 — 交互模型可移植性确认；TUI / GUI 前端选择推迟

日期：2026-08-30
状态：**已定向**（项目所有者确认）
关联：ADR-002（Human Console 交互模型）、ADR-012（Neovim/TUI 首期人机控制台）
原型：
- Neovim / TUI 形态：`https://claude.ai/code/artifact/1952acf6-ecfa-4fba-80c0-fba8db69c996`
- Tauri / GUI 形态：`https://claude.ai/code/artifact/7a1fb2e4-1dac-4652-b2d8-3a08be01da72`
（同一套双工作台模型、同一批数据、同一批场景，分别用 TUI 和 GUI 实现。）

---

## 决定

1. **ADR-002 的双工作台交互模型是前端无关的。** 用 Neovim（tabpage + 模态 + fold + telescope）
   和用桌面 GUI（分段控件 + 无模态编辑 + 内联 diff + 命令面板）分别实现，功能与交互**等价**
   —— 项目所有者对着两版原型的判断。模型不依赖任何一种前端技术。

2. **TUI 还是 GUI，推迟到真正做 UI 的阶段再定。** 现在不定。理由：
   - 两版手感是平的，所以这不是一个"哪个体验好"的问题。
   - M1 的责任是"读投影足以支撑两个镜头"，这条**与前端无关**；`M1-DESIGN.md` §10 的
     Console 读投影充分性验收（M1.9 执行）已经覆盖它。
   - 因此这个选择对 M1.0–M1.9 **零影响**，不阻塞任何里程碑。

3. **低后悔默认：确认 ADR-012（首期 TUI）。** GUI 作为**已评估的二期选项**保留，连决策标准
   一起记在下方，届时不从零重吵。等价于 C 方案（首期 TUI 打通数据面，GUI 二期）。

---

## 决策标准（UI 阶段用这张表拍板，不要重新发明）

| 维度 | Neovim / TUI | Tauri / GUI |
|---|---|---|
| **"替代 IDEA" 天花板** | `jdtls` 封顶：重构（Extract Interface / Change Signature）、图形调试器、Spring 感知导航（bean 图 / 配置提示 / JPA 校验）都差一截。 | 可接 Monaco / tree-sitter + 自研 LSP 编排 + 图形调试器，上限高得多。 |
| **构建 / 维护成本** | 一份 Neovim 配置（Lua）+ 3 个自定义 buffer + 1 个 telescope picker + 状态栏取数；其余全是成熟插件配置。 | 在造编辑器：窗口管理、编辑器组件、全部 chrome 自己扛，即便用 Tauri「轻量」也是拥有整个前端。 |
| **目标用户** | 已经住在 Neovim 里的人：零摩擦。 | 从 IntelliJ 迁出来的人：软着陆。 |
| **到可用 v1 的时间** | 快（配置 + 胶水层）。 | 慢（先得有个能用的编辑器）。 |
| **体积 / 内存**（量级参考） | ~15 MB / ~40 MB。 | Tauri ~10 MB 二进制 / ~80 MB 内存（Electron 则 150 MB+ / 300 MB+，不在选项内）。 |
| **AI CLI 集成落点** | 内置终端（`toggleterm`）。 | 底部 dock 的终端面板。 |

**触发重新评估的信号**（出现任一，把这个决定拿回来重议）：
- 首期 TUI 实际使用中，Java 工具链深度成为高频阻塞（重构 / 调试 / Spring 导航天天卡）。
- 目标用户群体明确不是 Neovim 用户，TUI 学习曲线成为采用障碍。
- 出现一个成熟可嵌入的 GUI 编辑器组件，把"造编辑器"的成本降到可接受。

---

## 对 M1 的影响

**无。** `M1-DESIGN.md` 的契约面、DONE 不变量、里程碑链全部不动。
本 ADR 只是把一个悬着的方向问题落定为"推迟 + 有标准 + 有默认"，并确认 ADR-002 的模型
不会因为前端选择而返工。
